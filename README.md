# 通用 Web 渗透测试流程工具包

> 版本：2026-09-08（源自实际渗透测试项目经验沉淀，已做产品无关化处理——无目标/凭据/接口硬编码）
> 组成：`web-pentest/`（生成侧：六阶段流程 + 授权预设 + 覆盖度硬规则 A-F + 报告模板）、`pentest-report-check/`（校验侧：L1/L2 两段式 R1-R10 语义校验）
> 相对上版（09-03b）新增：授权预设（内部测试环境写操作默认授权）、覆盖度硬规则 A-F 六条 + 产品知识库闭环、finding 七要素/U 项六要素（实测响应独立字段）、争议定级取最高级（§7.6）、未闭合项闭合度核查（终审固化）。

## 一、部署到新终端

1. **本包**：解压到 `~/.agents/skills/`（Windows 即 `C:\Users\<用户名>\.agents\skills\`），得到 `web-pentest/` 与 `pentest-report-check/` 两个 skill。skill 内路径均为用户相对路径，用户名不同不影响。
2. **ZCode CLI + 插件**：安装 ZCode CLI 后从官方 marketplace 装 `browser-use`、`computer-use`、`document-skills`（报告 docx/pdf 导出用）。
3. **工具栈**：docker 起 kali-pentest 容器（nmap/sqlmap/nuclei/whatweb/nikto/openssl 等）。
4. **网络**：新终端须能路由到目标产品的管理口；出口 IP 变化须先核对授权范围覆盖。

## 二、授权预设与红线（2026-09-04 规则更新）

### 默认授权（无需逐项确认）

被测目标均为**内部测试环境**且测试任务具有用户授权（含写操作权限）时，以下默认放行：

- 写操作类 payload（真实改密、创建/删除账号、上传 webshell、SQL 写库、命令执行写文件）
- 破坏性测试（DoS/压力——建议放最后单独执行，致不可用会中断其余测试项）
- 数据库读写（含 schema 变更——护栏：先快照/备份记录）
- B 档主动验证类（sqlmap/ZAP/hydra 等）

**写操作护栏**（执行纪律，不是授权门槛）：写/删优先落一次性测试对象（可辨识命名如 `pentest_tmp_01`）；每步请求+响应存证据目录；测试产物测毕清理或登记到报告。

### 保留红线（授权预设不覆盖，执行前必须停下问用户）

- **外发数据到公网第三方平台**（DNSLog/oast 等）——数据出域不是目标系统权限问题；替代路径：内网自建回连接收端
- **公开发布**测试结果、提交公开漏洞库
- **环境属性不符停问**：目标呈现生产特征（真实业务流量/真实用户数据/对外服务）→ 暂停确认
- **凭据纪律**：凭据/token 不进代码、不进 commit、不进日志、不进工作目录
- **授权范围外目标**一律不测（法律前置）；无授权拒绝执行

## 三、对新产品启动测试（流程入口：`web-pentest/SKILL.md`）

### 0. 启动信息完备性（第一动作）

首次收到渗透测试请求先盘点四项：①产品地址（URL/IP+端口）②前端凭证（≥1 登录账号）③后台凭证（SSH/DB，决定灰盒）④前端多个不同权限的用户（越权/权限模型测试前提）。**缺项先提醒用户补齐并说明影响，不得默默降级开跑**；用户确认"先跑现有条件"才启动，缺口记入待补清单、报告如实标注。

### 1. 预检（00-preflight，无授权不启动）

书面授权 + IP/端口/应用边界 + 授权级别逐项确认，摘要落盘 `00-授权/授权范围.md`（不含凭据）；按工作目录模板初始化（00-进度状态 / 00-授权 / 01-测试方案 / 02-侦察报告 / 03-测试报告 / 04-补测清单 / 05-工具脚本 / 06-灰盒产物，每个产品独立目录）。凭据文件在工作目录之外单独存放（600 权限），`scripts/auto-login.sh` 全参数化。**同时执行覆盖度硬规则 A 前半**：向委托方索取历史安全资产（过往渗透报告/漏扫清单/厂商 advisory）+ 检查本地产品知识库，获得即反提为回归测试清单并入测试矩阵。

### 2. 六阶段流程

```
预检 → 侦察 → 灰盒 → 黑盒 → 确认 → 报告
```

- **侦察**：端口/指纹/技术栈 + 接口清单**四选多采集**（browser-use 登录采集/外部抓包导入/手动清单/静态分析+灰盒路由表，至少一种可叠加）+ 路径枚举；识别出"反代+后端应用"双层结构即登记为黑盒必测项（硬规则 C 前置）
- **灰盒**：配置/组件/反编译/硬编码凭据审计；**系统内置账号清点**（/etc/passwd 逐个核对默认凭据，硬规则 D）+ **高危 sink 全仓对账**（SQL 拼接逐点三态登记，硬规则 E）；拿灰盒路由表后与矩阵做**模块级对账**（硬规则 B）
- **黑盒**：注入（E1-E14 入口全覆盖，BLOCKING）/XSS/越权/CSRF/SSRF/上传/会话/安全配置 + **反代双层架构差分**（`..;/`、`//`、`%2e%2e%2f` 等变体集，硬规则 C）
- **确认**：实弹验证/代码层确认/降级记录——判断方式四分类如实标注（黑盒实弹/灰盒确认/代码层确认/降级），不把代码层确认冒充实弹
- **报告**：见第五节

每阶段过 `phase-gate.sh` 阶段闸门（A4）；A1 测前查重、A2 写操作守卫、A3 证据校验、A5 续传自检全程前置。断点续传靠 `00-进度状态.md`（事件驱动存档）+ `resume-check.sh`。

### 3. 贯穿全程

遗漏清单回顾（`gaps-checklist.md` 12 类）／覆盖度硬规则 A-F／凭据纪律／封禁规避节奏（封禁即暂停，不盲扫）。

### 4. 测试终止判据（双层，不要求 100% 实弹覆盖）

- **机器硬闸**：`phase-gate.sh 6` 四条——①矩阵无裸 `[ ]` ②补测清单无裸 `- [ ]` ③红线登记无 `[待确认]` 拋留 ④未闭合项已进报告且满足闭合度（已测至闭合，或给出当前工具/环境不满足的具体条件——"时间窗/未安排"不构成合法理由）
- **人工判断**：边际收益递减 + 够不够交付，由人判断不脚本化

## 四、覆盖度硬规则 A-F（2026-09-07 规则更新）

> 成因：一次实测交付后与该产品历史漏洞清单对照，暴露三类静默漏项。六条全部为流程性规则（适用任何产品/技术栈）；产品特定情报由产品知识库 `~/.agents/product-kb/` 承载（A/F 闭环）。

| 规则 | 内容 |
|---|---|
| **A 历史漏洞回归** | 双向闭环：测试前索取历史安全资产反提为回归清单（每条三态：重现验证/已修复验证/不适用）；定稿前把新发现+历史未测条目回填产品知识库 |
| **B 模块级全量登记** | 路由枚举的每个模块必落三态之一：已测（矩阵行）/结构性排除（理由）/范围外（报告声明）；三类之和不等先查漏再进黑盒 |
| **C 反代双层差分** | 识别出反代+后端双层结构即黑盒强制加测绕过变体集（`..;/`、`//`、`%2e%2e%2f`、大小写、`;x=`），目标为反代规则不允许访问的后端独有应用 |
| **D 内置账号清点** | 灰盒持主机权限时枚举 /etc/passwd 全部账号逐个核对默认凭据，有 shell 的实测登录；认证类产品必查 |
| **E sink 全仓对账** | 高危 sink 审计产物逐点闭环登记三态（已验安全/实证漏洞/待验）；SQL 拼接类强制全量，报告引用对账数不得写"抽查未见" |
| **F 收尾核对** | ①授权项收尾核对（`[已授权]` 条目逐项核对执行状态）②范围外攻击面显式声明（"没测"必须在报告有迹可查）③产品知识库回填 |

## 五、报告与定稿

- **每条漏洞 7 字段**：定义 / 发现过程（判断方式）/ 影响 / 归属 / 修复建议 / 复现命令 / **实测响应**——缺字段不算定稿，只有命令没有实测响应无法证实漏洞；未实弹项如实条件性标注（"（择机）""（观察页面行为）"），数据源与发现过程一致
- **U 项（已测未发现）六要素**：测试内容 / 判断方式 / 复现命令 / 实测响应 / 结论 / 证据——U 记录是覆盖面的证明，与 finding 同等纪律
- **定级块三件套**：定级依据 + 反方论证 + 复评触发条件；条件性风险双态制（当前级 + 触发后级 + 触发条件）
- **争议定级取最高级**（`auto-decisions.md` §7.6）：内部核查后存在定级争议的，一律按争议范围内最高级定级，不停下等裁决；反方论点+维持理由留档，用户明示裁决优先
- **双轨终检**（phase-gate 之后、定稿之前，两道都要过）：①结构审计（fresh-context，含**未闭合项闭合度核查**——逐条过 G 表，非客观阻塞原因一律打回）②语义校验（`pentest-report-check`，见下节）
- **定稿**：双轨全过 + 终检后报告零修改（sha256 锚点核验）+ 收尾核对三项完成（授权项核对/范围外声明/知识库回填）才宣告终版

## 六、校验侧使用（`pentest-report-check/SKILL.md`）

对已完成的渗透测试报告做质量校验（不是重新测试，只读报告 + 查 NVD 等公开源）：

1. **阶段 1 反提**：从 L1 markdown 报告反提结构化侧车 `findings.yaml`（finding / not_found / gap 三类，schema 见 `findings-schema.yaml`）
2. **阶段 2 校验**：逐条跑 10 规则——R1 证据充分性 / R2 可利用性一致 / R3 CVE 核对 NVD / R4 措辞升级 / R5 降级溯源 / R6 复现可执行（含实测响应字段）/ R7 覆盖一致 / R8 双向一致 / R9 未测当已测 / R10 全级别七要素同构
3. 输出每条 通过/降级/剔除/待复核 + 汇总；真实凭据一律占位符化

## 七、纪律提示（skill 内已固化）

- 审计发现即修；定级争议按 §7.6 取最高级不停问；新漏洞验证/保留红线操作停下问用户
- 报告发布属红线，须用户确认
- 本仓库为通用规则发布渠道：是否推送、何时推送完全由用户决定，测试工作区产物（报告/证据/矩阵/凭据）永不入库
